# 实验三：无人机中继收益验证

## 文档状态（2026-05）

当前版本的 `experiment3_uav_relay.py` 已把新增 8 个内容/缓存 baseline 接入原始 UAV 中继实验，最终 `metrics.json` 会同时包含 11 个方法：

- 原始中继方法：`baseline1`、`baseline2`、`your_method`
- 桥接接入方法：`nocache`、`lce_lru`、`greedy`、`madrl`、`submod`、`spacecache`、`myopic`、`otcp`

这些新增方法通过 `algorithms/code/project_experiment_bridge.py` 适配到本实验：每个 UAV 的持续业务流被映射到一个固定 `content_id`，放置方案再被还原为“当前图上是否存在可服务路径”。因此，本 README 里优先用成功率、盲区救援率、恢复时间来解释跨族结果；绝对时延和过载统计仍带有各自实现的原生模型含义。

当前版本额外引入了两项参数调节来避免新增算法全部塌成 100%：

- 时变热点内容窗口：每个 UAV 不再永远请求同一个内容
- 业务时限：超过时限的内容服务记为失败，因此是否提前放对内容会直接影响盲区救援率和成功率

## 实验目标

验证在**卫星接入盲区/遮挡场景**下，引入 UAV 作为空中中继节点能够显著提升业务连续性，核心命题：

> **当部分无人机失去直连卫星能力时，协同中继比“无中继”或“被动中继”更稳定、更高效。**

本实验延续实验 1、2 的组织方式，但关注点从“缓存收益”和“动态拓扑稳定性”切换为**UAV 作为中继节点的接入补盲能力**。

## 实验设计

### 基础拓扑

使用真实轨迹构建 4SAT + 5UAV + 1GS 三层网络：

| 参数 | 值 |
|------|-----|
| 卫星轨迹 | `traces/sat_trace_4/` |
| UAV 轨迹 | `traces/uav_trace/uav_trace_full_5uav.csv` |
| 时间步数 | 200 步 |
| 中心服务器 | `GS_01` |
| SAT-UAV / SAT-GS 带宽 | 20 Mbps |
| SAT-SAT 带宽 | 100 Mbps |
| UAV-UAV 中继带宽 | 12 Mbps |
| UAV-UAV 最大中继距离 | 2.5 km |

### 盲区/遮挡注入

为了让“无人机中继”成为必要能力，本实验在真实轨迹上叠加**可预测卫星盲区窗口**：

- `UAV_01`: `[70,115)`, `[160,195)`
- `UAV_02`: `[20,75)`, `[120,170)`
- `UAV_03`: `[15,95)`, `[110,165)`
- `UAV_04`: `[40,130)`
- `UAV_05`: `[25,70)`, `[85,155)`, `[165,200)`

在盲区窗口内，该 UAV 的所有 `UAV-SAT` 链路被切断；在进入盲区前的 3 步过渡窗口内，卫星接入时延会被放大，模拟遮挡逼近和链路质量恶化。

### 业务模型

- 每个时间步，5 个 UAV 各向 `GS_01` 发起 1 条持续业务流
- 业务负载大小：1 MB
- 若该步发送失败，则视为业务超时并记入 `1200 ms` 超时惩罚

因此，本实验的“业务完成时延”不是单纯的物理传播时延，而是：

$$
T_{service} = T_{propagation} + T_{transmission} + T_{relay\ overhead} + T_{queue}\, ,
$$

若失败，则记为：

$$
T_{fail} = 1200\ ms
$$

这使得“是否能在盲区期间持续交付”会直接影响平均业务时延。

## 对比算法

### Baseline 1：无中继直连

- 仅允许 `UAV -> SAT -> ... -> GS` 直连路由
- 一旦 UAV 落入卫星盲区，则该业务直接失败
- 不使用任何 UAV-UAV 中继链路

特点：

- 实现最简单
- 对盲区极其敏感
- 恢复只能等到卫星重新可见

### Baseline 2：被动单跳中继

- 当直连失败后，等待 1 步再尝试寻找中继 UAV
- 只选择**单跳最近**的可用中继 UAV
- 不考虑中继能量、未来盲区风险和负载均衡

特点：

- 比“无中继”更强
- 但容易把流量集中压到最近的 UAV 上
- 遇到热点中继过载或低能量时，成功率仍明显下降

### Your Method：主动式负载均衡中继

核心思想：

1. **遮挡前瞻**：对即将进入盲区的 UAV 提前预选中继
2. **中继评分**：按多因素打分选择 relay

评分由以下部分构成：

- 中继稳定性（未来是否即将进入盲区）
- 剩余能量
- 空闲容量/当前负载
- 几何邻近性（源 UAV 到 relay 的链路代价）

3. **优先避免热点 relay**：如果当前首选 relay 已接近过载，则切换到次优但更空闲的 relay
4. **盲区零等待切换**：当直连失效时，直接启用预选 relay，无需像 Baseline 2 那样等待检测周期

因此，该方法本质上是：

> **“遮挡预测 + 负载均衡 + 能量感知”的协同中继策略**

### 新增 8 个内容放置 baseline（桥接接入）

新增方法来自 `algorithms/code/`：

- `nocache`
- `lce_lru`
- `greedy`
- `madrl`
- `submod`
- `spacecache`
- `myopic`
- `otcp`

在本实验里，它们不是原始意义上的“中继调度器”，而是通过内容放置结果来决定是否能从某个可达节点取得内容。因此，这组结果更接近“在盲区场景下的可服务性上界”，而原始三方法仍负责体现中继负载、能量、等待与预测策略之间的差异。

## 评估指标

| 指标 | 含义 | 目标 |
|------|------|------|
| **任务成功率** | 所有请求中成功送达的比例 | 越高越好 |
| **业务完成时延** | 成功时延与失败超时统一统计后的平均业务时延 | 越低越好 |
| **盲区救援率** | 处于卫星盲区的请求中，有多少能通过 UAV 中继成功送达 | 越高越好 |
| **平均恢复时间** | UAV 进入盲区后，业务重新恢复可用所需的平均步数 | 越低越好 |

补充统计：

- `overload_events`: 中继热点过载次数
- `relay_usage`: 中继路径被使用的总次数

这些补充指标保存在 `metrics.json` 中，用于后续分析，但不作为本实验的 4 个主展示指标。

### 当前版本的读法

1. 在原始三种中继方法里，`your_method` 仍然最好，说明主动式负载均衡中继对真实盲区补盲最有效。
2. 新增 8 个方法现在已经被明显拉开：`otcp` 仍然是桥接组里的最强者，`submod/myopic` 次之，`lce_lru/greedy/madrl` 在时变热点下表现明显更弱，`nocache` 则被压到 0%。
3. 这说明在盲区场景里，是否能提前把热点内容布到未来可服务节点，比“只要图上存在某条路径就算成功”更关键。
4. 这组新增方法仍不建模原始三方法中的中继等待、热点过载与能量约束，所以 `overload_events`、绝对时延等指标不应直接与原始三方法做控制策略层面的结论对比。

换句话说，Experiment 3 现在同时提供两层视角：

- 原始三方法：看真实中继策略差异
- 新增八方法：看内容放置在盲区场景下的可服务性差异

## 实验结论

实验三从“遮挡补盲”的角度补齐了实验 1、2 之外的另一类能力验证：

- 实验 1 证明“缓存 + 路由协同”有收益
- 实验 2 证明“动态拓扑下你的方法更稳”
- **实验 3 进一步证明：在卫星接入失效时，UAV 中继能够把大量原本会中断的业务重新接上，而且主动协同中继明显优于被动反应式中继；同时，桥接接入的内容放置方法还能作为“可服务性上界”补充这一场景的解释。**

因此，这组实验可以形成一条比较完整的论证链：

1. 有缓存协同时更高效
2. 在动态拓扑下更稳定
3. 在接入盲区下还能依赖 UAV 中继维持连续服务
